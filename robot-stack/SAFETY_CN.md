# 安全须知 —— 在底层控制 / 学习式控制下操作真实人形机器人

[English](SAFETY.md)

> **英文版 [SAFETY.md](SAFETY.md) 为权威版本。** 本译文供参考；如两版有出入，以英文版为准。
> 若您发现译文中存在会影响操作判断的偏差，请指出——我们会更正。

本文是在真实人形机器人上运行电机级控制时**不可协商**的安全层，涵盖：速度行走、
`rt/arm_sdk` 叠加控制，尤其是**全身 RL 策略部署**（`rt/lowcmd`，且厂商平衡控制器已释放）。
它是从一次真实事故中写出来的 —— 在使用任何一项实机控制技能之前先读它
（[deploy-policy](https://github.com/arm/arm-dc-nvidia-isaaclab/blob/main/skills/deploy-policy/SKILL.md)、[locomotion](https://github.com/arm/arm-dc-unitree-g1/blob/main/unitree/g1/locomotion/README.md)、
[controller](https://github.com/arm/arm-dc-unitree-g1/blob/main/unitree/g1/controller/README.md)）。

本文适用于一般人形机器人；G1 特有之处会单独标出。

## 0. 首要铁律

> **绝不要对一个正在向真实机器人发送底层电机指令的进程执行强杀（`kill -9` / `SIGKILL`）。
> 强杀是"停止"的反面。**

当 `rt/lowcmd`（或任何电机指令话题）的发布方在没有发出最后一条安全指令的情况下死掉时，
机器人的电机控制器会继续按**它收到的最后一条指令**动作 —— 那是一个*以设定刚度保持的位置目标*。
DDS 层让情况更糟：写端的**最后一个样本会持久化**给电机订阅方（而且缓冲中的样本可能在写端被拆除时
被刷出去），于是那个过期的高增益目标会持续施加，而已经没有任何东西能更新或阻尼它。
如果那些是迁移/仿真增益下的策略目标（在 G1 上 `kp` 可达 **150–200**），关节就会**硬顶着**
朝那个姿态驱动，既没有后续更新，也没有任何补救。在一台已经倒地或无支撑的机器人上，
这就是一次剧烈的失控。

**它当时的样子（2026-06-12，G1 全身"床边伸手"部署）：** 一次在龙门架上运行的全身策略没有迁移成功；
操作员按下了手柄的**中止键，它正确地把机器人阻尼住了**。部署进程当时还活着，于是有人对它
`kill -9`，"想停掉指令"。那次强杀把最后一条高增益伸手指令锁存在了电机上，而已经没有发布方
能更新或阻尼它 —— 机器人**在地上旋转踢腿，打碎了一扇窗户。** 中止键是正确的停止方式；
强杀把它撤销了。

`SIGKILL` 无法被捕获，所以进程无法在退出途中做阻尼。这正是*为什么*你绝不能把它当作停止手段 ——
也是为什么每一个部署进程都必须安装一个可捕获信号的阻尼处理器
（见 §2，`lib/safe_stop.py`（arm-dc-robotkit 的 `lib/safe_stop.py`））。

## 1. 停止手段的层级（权威性从高到低）

在任何运动之前，始终保证更高层级的手段实际伸手可及。

1. **硬件急停 / 断电** —— 唯一*有保证*的停止方式。不论软件处于什么状态，它都切断电机电源。
   每一次运行都要有一只手放在它/电池上。
2. **手柄固件阻尼 —— `L2+B`** —— 手持设备固件层的阻尼。由固件处理，因此**即使你的控制进程已经挂起、
   或 DDS 已经卡死，它依然有效**；它把关节置为**柔顺**状态（`kp→0`）。当软件已经帮不上忙时，
   这就是兜底。
3. **回路内"任意键"中止（运行期间的主要中止手段）** ——
   [`G1Remote`](https://github.com/arm/arm-dc-unitree-g1/blob/main/unitree/g1/controller/README.md) 的
   **任意键锁存**被接进了控制回路：操作员按下**任意一个键**，回路在约 20 ms 的一个 tick 内捕获它，
   对**所有**关节执行干净的 `kp=0, kd≈small, tau=0` 阻尼（或者释放手臂叠加控制），然后退出。
   你**绝不应该为了停止一次运行而去找某个特定的组合键 —— 乱按任意键即可。**
   这就是回路每个 tick 轮询的东西，也是 `SafeStop`（arm-dc-robotkit 的 `lib/safe_stop.py`）
   所阻尼的东西。它由软件中介，所以万一回路本身卡死，第 1–2 层仍是兜底。
   ⚠️ **任意键锁存只有在 Develop 模式下才是*干净*的中止**（此时厂商控制器被暂停，按键没有绑定手势 ——
   它们只是回路读取的比特位）。在 **Regular / AI-Sport 模式下，`A/B/X/Y` 组合键会触发厂商手势例程**，
   *并且同时*触发锁存，所以在那些模式下优先使用 `L2+B` / 急停。在任何运动之前，
   始终**在你将要运行的那个模式下**执行 `confirm_abort_live`（按下+松开，观察锁存是否触发）。
   （退出 Develop 模式本身要**重启**机器人 —— 没有任何软件手段能重新接管厂商控制器。）

**杀进程不在这个清单上。** 如果必须终止一个进程，**先阻尼（任意键）、确认机器人已柔顺、再终止** ——
而且永远不要用 `-9`。

## 2. 信号安全的部署（任何 `rt/lowcmd` / `rt/arm_sdk` 进程都必须做到）

每一个下达电机指令的进程都必须保证在**每一种**退出路径上都做阻尼 —— 正常返回、异常、
`SIGINT`（Ctrl-C）以及 `SIGTERM`（不带 `-9` 的 `kill`）。使用
`lib/safe_stop.py`（arm-dc-robotkit 的 `lib/safe_stop.py`）：

```python
from arm_dc_robotkit.safe_stop import SafeStop

def damp():               # command compliant on ALL joints (kp=0, kd≈3, tau=0), ~1 s
    g1.publish_damp(seconds=1.0)

with SafeStop(damp):      # damps on return, exception, SIGINT, SIGTERM
    run_control_loop()    # ... your 50 Hz loop, polling the controller abort each tick
```

`SafeStop` 无法防护 `SIGKILL`（不可捕获）或断电 —— 那恰恰就是上面第 1–2 层存在的理由。
它消除的是*可捕获*的失败模式，使得剩下的每一条退出路径都让机器人保持柔顺。

另外还要准备一个**独立的紧急阻尼脚本**，可以从第二个 shell 里运行
（[`lib/safe_stop.py --panic` 模式]）：它会打开自己的发布方，向所有关节泛洪 `kp=0` 阻尼指令。
用它可以在*不靠近机器人*的情况下让它变成惰性状态。

## 3. 降险阶梯 —— 把全身策略部署到真实的腿上

一个全身平衡策略的首次仿真→实机迁移，**只要有任何一处不对就会摔**（关节顺序、观测缩放、
不可观测的基座速度项、接管姿态的落差）。失败是**快速的**（亚秒级，快过反射性的抓扶），
不是渐进的。所以要分级推进；每一级都是下一级的闸门：

| 台阶 | 运行什么 | 摔倒风险 | 通过条件 |
|---|---|---|---|
| **0 —— 离线** | 构造实时观测、运行策略、**打印**观测与动作。不下达任何指令。 | 无 | 观测合理（重力 ≈ `[0,0,-1]`）、**关节顺序已验证**（预测的姿态偏移落在正确命名的关节上）、动作有限且有界 |
| **1 —— 局部、摔不倒** | 策略运行，但**只施加一个不会让机器人倒下的子集**（例如通过 `rt/arm_sdk` 控制手臂，腿仍由**厂商平衡控制器**掌管）。动作混合、限速、钳位、中止已就位。 | 无（腿由厂商掌管） | 平滑、有界、可中止；IMU 保持水平（腿不受影响） |
| **2 —— 完整全身** | 所有关节通过 `rt/lowcmd`。操作员已**手动**把机器人置于**底层 Develop 模式**；代码只**验证**这一点，**不**在软件里释放厂商控制器。移动到默认姿态 → 混合 → 策略。 | **高 —— 可能摔倒** | **Develop 模式已验证**、**中止已在该模式下实测证明**、**双脚着地 + 龙门吊架留余量**（**不是**完全悬吊）、急停伸手可及、区域清空 |

**任何手臂能完成的有用任务，都强烈优先选择台阶 1。** 手臂叠加在厂商平衡之上，能以**零全身平衡风险**
完成一次伸手，而且不需要龙门架。只有当任务**可被证明**需要厂商平衡器提供不了的腿部/质心控制时，
才去做台阶 2。

**台阶 2 需要支撑 —— 但不是悬吊。** 使用一套**留几厘米余量的龙门架/吊具**，机器人**双脚着地**：
它自己承重、自己平衡，吊具在几厘米内接住一次跌倒。**不要把它完全吊起来：** 平衡策略假定存在
地面反作用动力学，所以完全离地时它处于**分布外 —— 乱扑腾是必然结果，而不是一个边角情况**，
而且你什么也学不到。对于亚秒级的腿部失效，"用手扶着"同样不够。
（一个没有视觉的策略伸向的是一个*目标坐标*，而不是它感知到的表面 —— 做平衡测试时**不需要**
把任务用的家具摆在它面前，而空出的场地会让一次跌倒更干净。）

## 4. 交接与增益（台阶 2 的具体事项）

- **交接到底层控制必须由人手动完成 —— 由操作员驱动，绝不是软件释放。** 旧的
  `MotionSwitcher.ReleaseMode()` 路径会在操作员以为机器人处于安全模式时夺走腿（§0 的事故）。
  改由操作员把 G1 手动切进底层 Develop 模式：

  | 动作 | 按键（固件 ≥1.4） | 说明 |
  |---|---|---|
  | **阻尼 / 急停** | **`L2+B`**（旧：`L1+A`） | 固件层的柔顺阻尼；操作员的急停；即使控制进程已挂起也有效 |
  | 锁定站立 | `L2+UP` | 从阻尼状态进入；请托住肩部 |
  | Regular / AI-Sport | `R1+X` | **在这里按键会触发厂商手势**（所以回路内任意键锁存在这个模式下*不干净*） |
  | **Develop / 底层 `rt/lowcmd`** | **`L2+R2`** | **前置条件：必须先悬吊 + 阻尼**；会暂停 AI-Sport；在这里**任意键都是干净的中止**；**退出 = 重启** |

  **顺序：悬吊 → `L2+B`（阻尼）→ `L2+R2`（Develop）。** 代码只做**验证** —— 但
  **不要用 `MotionSwitcher.CheckMode()`，它会说谎：** 在 G1 EDU 上，无论是 AI-Sport 还是刚进入的
  Develop 模式，它都返回*配置的*模式（`name='ai'`），而 `rt/sportmodestate` 在这个变体上对此保持沉默 ——
  两者都说不出平衡器究竟有没有在运行（已实机验证；与 unitree_sdk2_python#43 相互印证）。
  可靠的信号是**高层服务的存活性**：一个只读的 loco GET-FSM RPC（`ROBOT_API_ID_LOCO_GET_FSM_ID`）
  **在平衡器运行时会应答（code 0），在它关闭时报错或超时**（Develop → code 3102，已实机验证）。
  `verify_whole_body_ready` 就以此为闸门：**服务应答 → 拒绝运行**（说明有控制器在活动）；
  **服务不通 → 继续**；**探测不可用 → 只有在操作员明确声明处于 Develop 模式时才继续**（故障安全）。
  **绝不要让 `rt/lowcmd` 去跟一个正在运行的高层控制器抢 —— 那会抖动/振荡，而不是干净地接管**
  （unitree_sdk2_python#43/#108）。
- **在 G1 EDU 上，优先选择摔不倒的手臂叠加，而不是全身接管。** 全身 `rt/lowcmd` 只有在高层控制器
  完全*关闭*（Develop 模式）时才成立 —— 在这个变体上，试图对着运行中的 AI 控制器驱动所有关节，
  会让腿跟它对着干。对于手臂任务（床边伸手），把机器人保持在 Regular/AI-Sport 模式，
  使用 **`rt/arm_sdk` 叠加**：它与控制器*混合*（`executed = controller·(1−w) + arm_sdk·w`，
  权重从 0 渐变到 1；unitree_sdk2_python#108）而不是与之对抗，摔不倒，也不需要龙门架。
  行走用厂商的 `LocoClient.Move` 驱动。全身 `rt/lowcmd` 是一条**只在龙门架上、作为最后手段的
  研究路径**，而在 EDU 上最好把它当作只做站立的实验，而不是任务路径。
- **除非**你把第一帧 `LowState` 里的 `mode_machine` 复制进每一个 `LowCmd`，并为每个被下达的电机设置 `mode=1`（FOC 使能），**否则 lowcmd 会静默地什么都不做** —— 这与上面的模式闸门无关
  （unitree_sdk2_python#44）。G1 绑定这两件事都做了。
- **中止手段是任意键 —— 先证明它有效。** 在 Develop 模式下，操作员必须能**乱按任意键**来中止
  （回路内锁存 → 干净阻尼；§1.3），绝不能去找某个特定组合键。`confirm_abort_live` 在任何运动之前
  强制执行这一点：操作员按下并松开手持设备，代码确认任意键锁存**在当前这个模式下**触发了。
  （这正是咬过我们的那个陷阱 —— 在 Regular 模式下，"中止测试"的按键触发了手势并让机器人失稳，
  所以锁存只有在 Develop 模式下才是*干净*的。）
- **`rt/lowcmd` 写端 QoS：显式 VOLATILE + keep-last-1。** 这样一个被拆除的写端就不会留下历史，
  中间件也就无法把它重传给电机订阅方。（这是 §0/§2 之后的纵深防御 —— 真正的保护是 SafeStop 的阻尼，
  以及绝不 `kill -9`。）
- **只有在你以增益下达默认姿态之后，腿才开始承重。** 底层 Develop 模式起始于零力矩/阻尼状态 ——
  裸模式*站不起来*（重量由吊具承担）。腿是在程序以**训练时的 PD 增益驱动默认姿态**（move-to-default）
  时才变成承重的，而**不是**靠厂商平衡器。这就是为什么你不能"从 Regular 模式启动"，
  也决定了启动顺序（对应 `unitree_rl_gym deploy_real`：零力矩 → develop → 移动到默认姿态 →
  放低吊具 → 策略 → 放松吊绳）。
- **消除启动瞬态，并对每一次过渡做混合**（一次突跳在手臂上无害，在腿上就是一次跌倒）：
  (1) 一段**脚本化、增益渐变**的动作，移动到精确的默认姿态（阻尼优先 —— kd 全程保持标称值，
  kp 逐渐升高），策略不在回路中；(2) 一个**操作员检查点** —— 保持默认站姿，等待操作员放低吊绳
  （**第 1 阶段**，双脚承重）并给出继续的信号；如果没有继续信号则**故障安全阻尼**
  （绝不自动启动策略）；(3) 以一个**中性指令**启动策略，并**逐渐加大指令**
  （操作员在稳定平衡后放低吊绳**第 2 阶段**）；(4) 完成时，在策略*仍在平衡*的状态下把指令
  逐渐降回中性来**收尾**（绝不做开环突跳），然后**轻缓地**把姿态归回默认并把 kp 降到 0；
  (5) **第一次全身测试就是站立**，只有在站稳之后才加入伸手动作。
- **匹配策略训练时的仿真 PD 增益**（G1 床边伸手：髋 100/2，膝 150/4，踝 40/2，腰 200/5，
  手臂 40/10）。增益错了 = 迁移不成立。（从部署契约里读取它们，这样它们就不会漂移；
  一个缺失增益的契约会发布 `kp=0` → 零力矩。）
- **中止 / 结束 → 底层阻尼**（`kp=0, kd≈3`），而不是杀进程（§0）。在龙门架下，之后由吊具托住机器人；
  退出 Develop 模式本身要重启。

## 5. 事故之后 —— 在**不靠近**的前提下让现场安全

1. **不要靠近一台刚刚失控跑掉的机器人。** 如果可以，先切断电源。
2. 从安全距离上，如果它仍在被下达指令，就用软件让它变成惰性：运行**紧急阻尼**（§2）——
   `kp=0` 的泛洪只可能让它变柔顺，不可能驱动出某个姿态。
3. **在靠近之前，用只读遥测确认它已惰性：** 订阅 `rt/lowstate`，在几秒钟内确认
   **最大 |关节速度| ≈ 0**、**最大 |力矩| ≈ 0**（是被动的，不是被驱动的）、**IMU 已冻结**，
   并且**没有任何进程在发布**那个指令话题。只有到这时才靠近 —— 最好从背后 / 避开肢体的摆动弧线；
   电机松弛时关节是可反向驱动的，而不是带电的。
4. 重新架设之前先断电（拔电池）。

## 6. 运行前检查清单（每一次实机控制运行）

- [ ] 硬件急停 / 电池伸手可及；操作员的手放在上面。
- [ ] 手柄中止**已就位**并已接进回路（[`G1Remote`](https://github.com/arm/arm-dc-unitree-g1/blob/main/unitree/g1/controller/README.md)）。
- [ ] 进程使用 `SafeStop`（arm-dc-robotkit 的 `lib/safe_stop.py`）（在返回/异常/SIGINT/SIGTERM 时阻尼）。
- [ ] 仅台阶 2：机器人挂在留有余量的**龙门架**上；区域清空；厂商释放已验证。
- [ ] 你知道在第二个 shell 里执行的**紧急阻尼**命令。
- [ ] 以**你亲眼所见**来验证，而不是靠遥测 —— 但在靠近之前要用遥测确认它已*惰性*。
- [ ] **下达的最高速度处于或高于该平台的步态下限。** 在 Go2 上大约是 0.35 m/s
      （`MIN_GAIT_COMMAND_M_S`）；低于它时，机器人会在被下达前进指令的情况下站着不动，
      并且不报告任何故障。这一条之所以出现在安全检查清单上、而不是只出现在导航文档里，
      是因为它对*诊断*的影响：编码器、状态估计器和失速闸门会一致认为机器人正被物理拽住，
      于是操作员被派去寻找一根并不存在的系绳或障碍物 —— 而花在错误物理原因上的时间，
      就是花在一台带电机器人旁边的时间。

> 在这个项目里，任何前提都值得质疑 —— **物理安全除外。** 在那里，一律采用最保守的停止方式，
> 绝不在运动过程中即兴发挥出一个"直接杀掉它"的捷径。
